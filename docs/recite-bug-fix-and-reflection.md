# 背单词两个 bug 修复 + 反思优化方案（2026-08-15）

> 用户实测发现两个脚本/AI 都漏掉的真实 bug，本文记录根因、修复、以及「为什么自动化测试没发现」的反思。

## 一、用户发现的两个 bug

### Bug 1：拼写题上面显示了大大的答案单词
- **现象**：拼写题要求用户拼写单词，但题目卡片顶部却**完整显示了答案单词 + 音标 + 发音按钮**——拼写失去意义，答案泄露。
- **根因**：RecitePage 的「单词 + 发音」头部是所有题型共用的，拼写题时也显示了 `current.word`。
- **修复**：拼写题时隐藏单词头部（`!isSpell && (...)`），只显示中文释义 + 发音提示 + 字母提示。

### Bug 2：中文释义选项词性标注不一致
- **现象**：看词选义的选项，有些带词性（`v. 运输，运送`），有些不带（`段落、通道`），视觉不一致，且用户可能靠「词性标记」猜出答案。
- **根因**：数据源不统一——旧 30 个手写词的 `meaning` 带词性前缀（`v./n./adj.`），新导入 1000 词（cet_full_list）不带。数据库实测 **22/1022 带词性**（就是旧词）。
- **修复**：前端统一 `stripPos()` 剥离词性前缀再展示，所有选项格式一致。

## 二、方向 B 低成本项（已同步做）

| 项 | 实现 |
|----|------|
| 拼写题加字母提示 | 显示首字母 + 下划线 + 字母数（`a___ 4 个字母`） |
| 听音选词选项加中文 | 英文选项旁加中文释义（`able 有能力的`） |
| 题型按难度渐进 | 新词只用「选义/听音」（先认识），复习词才考验「拼写/发音」 |

## 三、反思：为什么脚本和 AI 都没发现这两个 bug

### 脚本逻辑问题（客观事实采集，无业务判断）
- 脚本只抓 `bodyText / 按钮 / 报错`，是**客观事实采集器**，不做「业务语义判断」。
- Bug 1：脚本抓到了「passage + 根据释义拼写单词」的文本，但**不会判断「拼写题不该显示答案」**这条业务规则。
- Bug 2：脚本随机到的词几乎全是新词（1000 个不带词性），旧词（22 个带词性）很少被随机到，**没暴露数据不一致**；即使暴露，脚本也不会判断「选项格式应一致」。

### AI 逻辑问题（开发者视角，无业务规则套用）
- 我看脚本输出时，是「检查功能是否渲染、是否报错」的**开发者视角**，不是「这个交互对用户是否合理」的**用户视角**。
- 我「看见」了「拼写题显示 passage」，但没「联想」到「拼写题泄露答案」——因为我的注意力在「题型渲染正常吗」，而非「题型设计是否正确」。
- 我「看见」了「选项日子/职业/段落、通道」，但没意识到「旧词带词性、新词不带，会不一致」——因为没把「数据一致性」纳入检查项。

### 根本原因
**测试缺「业务规则校验层」**：
- 第一层（脚本）：客观事实采集 —— 已做，但只回答「页面有什么」
- 第二层（业务规则）：人工定义规则 + 逐条核对 —— **缺失**，回答「页面是否符合预期」

## 四、反思优化方案

### 1. 脚本层面：加「业务规则断言」
给可用性测试脚本加 `ASSERTIONS` 配置，人工定义业务规则，脚本自动核对：
```js
ASSERTIONS: [
  { route: '/recite', when: '拼写', assert: '页面不应出现答案单词（出现即泄露）' },
  { route: '/recite', when: '看词选义', assert: '4 个选项词性格式一致' },
  { route: '/recite', when: '听音选词', assert: '每个选项都有中文释义' },
]
```
脚本执行时，`when` 命中则检查 `assert` 是否满足，不满足标记为「业务规则违规」。

### 2. AI 分析层面：建立「产品业务规则清单」
每次测试前，先列一份「这个产品应该遵守的业务规则」，测试时逐条核对，而不只是看「渲染/报错」：
- 拼写题：不泄露答案
- 选择题：选项格式一致
- 数据：新旧数据字段格式统一
- 文案：数字口径能对上（如 33 = 刚学 + 学习中 + 已掌握）

### 3. 流程层面：测试分两层
1. **第一层（脚本自动）**：客观采集 + 业务规则断言（可自动化的规则）
2. **第二层（AI + 用户）**：语义判断 + 用户视角（规则断言覆盖不到的「体验」问题，如「音标对零基础是障碍」）

### 4. 关键教训
- **「看得见」≠「看得懂」**：脚本能抓取全部文本，但「拼写题显示答案」这种业务语义错误，需要**业务规则**才能发现。
- **开发者视角会漏掉用户视角的问题**：必须假设自己是用户（尤其「什么都不懂的用户」），才能发现「数字对不上」「词性不一致」「答案泄露」这类体验问题。
- **数据一致性是隐形的 bug 源**：新旧数据字段格式不统一（词性），平时不报错、功能正常，但用户体验割裂——这类问题最容易被「只查报错」的测试漏掉。
