# 背单词两个 bug 修复 + 测试方法论重构（2026-08-15）

> 用户实测发现两个脚本/AI 都漏掉的真实 bug。本文记录根因、修复，并**重构测试方法论**——从「规则枚举」升级为「用户旅程模拟」。

## 一、用户发现的两个 bug

### Bug 1：拼写题上面显示了大大的答案单词
- **现象**：拼写题要求用户拼写单词，但题目卡片顶部却**完整显示了答案单词 + 音标 + 发音按钮**——拼写失去意义，答案泄露。
- **根因**：RecitePage 的「单词 + 发音」头部是所有题型共用的，拼写题时也显示了 `current.word`。
- **修复**：拼写题时隐藏单词头部（`!isSpell && (...)`），只显示中文释义 + 发音提示 + 字母提示。

### Bug 2：中文释义选项词性标注不一致
- **现象**：看词选义的选项，有些带词性（`v. 运输，运送`），有些不带（`段落、通道`），视觉不一致。
- **根因**：数据源不统一——旧 30 个手写词 `meaning` 带词性前缀，新导入 1000 词不带。数据库实测 **22/1022 带词性**（就是旧词）。
- **修复**：前端统一 `stripPos()` 剥离词性前缀再展示，所有选项格式一致。

## 二、方向 B 低成本项（已同步做）

| 项 | 实现 |
|----|------|
| 拼写题加字母提示 | 显示首字母 + 下划线 + 字母数（`a___ 4 个字母`） |
| 听音选词选项加中文 | 英文选项旁加中文释义（`able 有能力的`） |
| 题型按难度渐进 | 新词只用「选义/听音」，复习词才考验「拼写/发音」 |

## 三、反思：上一版诊断错在哪

上一版我把根因归结为「缺业务规则校验层」，于是给了「ASSERTIONS 规则断言」方案。**这个方向是错的**，因为它建立在三个错误假设上：

1. **假设规则可以提前枚举**——错。规则是「先遇到 bug 才事后总结」的，规则清单永远落后于 bug。这次能写「拼写题不泄露答案」，是因为 bug 已经发生了；下一个 bug 长什么样，我们并不知道。
2. **假设枚举足够全就能覆盖**——错。产品会变、用户会变、场景会变，能出问题的地方是**无穷的**，无法穷举。
3. **假设体验问题能写成 if-then**——错。Bug 1 勉强能写成规则，Bug 2 本质是**数据一致性问题**；而「音标对零基础是障碍」「产品定位错位」这类体验/定位问题，根本写不成规则。

### 真正的根因

不是「缺规则」，而是**测试方法把「查错」当成了「体验」**：

- 脚本回答「页面有什么」（客观事实）
- AI 回答「有没有报错」（表层检查）
- **但没人回答「用户带着目标来，能不能顺利、愉快地完成」**（本质问题）

**核心：测试的本质不是「找出不符合规则的地方」，而是「验证用户能否达成目标」。** 一旦把测试还原成「用户达成目标的过程」，所有问题——包括想不到的——都会自然浮现，不需要预先枚举。

## 四、本质方案：从「规则枚举」到「用户旅程模拟」

### 核心理念

不枚举「该检查什么」，而是**重建「用户使用产品的真实过程」**：一个会受挫、会困惑、带着目标来的真实用户，从头走到尾，问题自然浮现。

### 五个要素

#### ① 用户画像库（Persona）——明确「谁在用」
不是抽象的「用户」，是具体的人，每个画像写清四件事：

```json
{
  "name": "小明",
  "背景": "大二，四级 430 擦线过，词汇量约 3000，怕背单词",
  "今天来干嘛": "背 20 个四级新词，再把昨天没记住的复习掉",
  "懂什么": "认识常见词，能看音标",
  "不懂什么": "词根词源完全没概念",
  "什么会让他放弃": "一上来就撞生僻词、拼不出单词、被评分打击"
}
```

画像至少 3 个：零基础（小红）、备考（小明）、职场提升（老张）。

#### ② 任务驱动（Task-based）——明确「来干什么」
测试不是「遍历页面」，而是「完成任务」。每个画像配真实任务，度量指标是**任务完成度**：

> 小明任务：「背 20 个新词 → 复习昨天不会的 3 个词 → 看今天打卡进度」

走查时记录：找到入口了吗？卡在哪一步？哪里想放弃？——**任务完成度本身就是产品可用性的直接度量**，比「有没有报错」本质得多。

#### ③ 体验六维走查（固定视角，非固定规则）——明确「爽不爽」
六个「看问题的角度」，是**开放式提问**，不是「这里应显示 X」：

| 维度 | 走查问题（开放式） |
|------|------|
| 认知负荷 | 这一步小明看得懂吗？需要什么前置知识？ |
| 信息一致性 | 跨页面的数字/格式/口径统一吗？ |
| 反馈即时性 | 操作后有没有明确反馈？ |
| 情绪挫败点 | 哪里会让小明想放弃？ |
| 路径可达性 | 入口好找吗？需要几步？ |
| 边界状态 | 空数据、极限数据、异常数据长什么样？ |

「固定视角」和「固定规则」的区别：视角不预设答案，规则预设答案。视角能发现规则编不出来的问题。

#### ④ 数据质量巡检（独立一类）——覆盖「数据一致性」这种隐蔽问题
Bug 2 这类问题不在页面上报错，功能也正常，只在**数据层**割裂。独立巡检四个项：

- **字段格式一致性**：`meaning` 是否统一带/不带词性（本次 bug 就是这里抓到的）
- **覆盖率**：多少词有词根/音标/例句/词频
- **新旧数据割裂**：旧 30 词 vs 新 1000 词的字段差异
- **异常值**：空值、超长、乱码、重复

#### ⑤ AI 换位思考协议（核心方法论）——解决「开发者视角」
AI 默认懂词根、懂 IPA，这是它和用户的**认知鸿沟**。协议强制三条：

1. **测试前声明立场**：「我现在是 X，我要 Y，我懂 Z，我不懂 W」——不声明清楚就开始看页面，一定会滑回开发者视角。
2. **主动降智**：把已知的领域知识暂时忘掉，用目标用户的知识水平理解界面（音标对我是常识，对小红是天书）。
3. **记录情绪，而非报错**：写下「我困惑了」「我想放弃」，而不是「功能渲染正常」。

### 用本次两个 bug 验证新方案能「事前」抓到

- **Bug 1（拼写泄露答案）**：任务驱动下，小明走到拼写题，看到答案直接抄——「拼写动作变得无意义」这个**体验事实**自然浮现，不需要预先知道「拼写题不该显示答案」这条规则。
- **Bug 2（词性不一致）**：数据巡检直接统计「`meaning` 带词性前缀的分布」，发现 22/1022 割裂——独立抓到的，不依赖页面断言。

### 新旧方案对比

| | 旧：规则断言 | 新：用户旅程模拟 |
|--|--|--|
| 出发点 | 枚举「该检查什么」 | 重建「用户使用过程」 |
| 覆盖范围 | 只能覆盖能写成 if-then 的功能 bug | 功能 + 体验 + 设计 + 数据 + 情感 + 定位 |
| 对新问题的适应性 | 出了新 bug 才补新规则（永远落后） | 真实过程自然暴露新问题（不需预枚举） |
| 对体验/情感 | 覆盖不了 | 通过换位思考覆盖 |
| 对数据一致性 | 覆盖不了 | 独立巡检覆盖 |

## 五、落地方式

1. **脚本改造**：`web-usability-tool` 增加 `persona.json`（画像库 + 任务）+ 「任务模式」（按任务驱动走流程，输出任务完成度 + 卡点记录），替代现在的「逐页遍历 + 抓文本」。
2. **AI 工作流**：测试前先读 persona → 走「换位思考协议」→ 用体验六维走查表逐维记录 → 数据巡检脚本独立跑一遍。
3. **数据巡检脚本**：独立脚本统计字段一致性 / 覆盖率 / 异常值，不依赖页面渲染。

## 五、二次反思：同类 bug 为什么漏检（听音选词泄露答案）

方法论落地后，用户又指出一个 bug：**「听音选词」题型顶部也显示大单词 + 音标，泄露答案**——和之前修的「拼写题泄露答案」是**同一类**。

但这次脚本明明跑到了听音选词，正文里也抓到了：

```
背单词 | 第 1 / 20 个 · 听音选词 | 新词 | 0% | job | /dʒɑːb/ | 播放发音 | 听发音，选择正确的单词 | job工作 | hand手 | take拿走 | mentor指导
```

**`job | /dʒɑːb/` 就躺在脚本抓到的文本里。不是脚本没看见，是我没看懂。** 为什么？

### 三个直接原因

1. **修 bug 时没「举一反三」**：修拼写题时，我改的是 `!isSpell`（反向排除——「除了拼写题都要显示」）。正确思路应是正向列举——「只有 meaning + pronounce 需要显示」。反向排除天然容易漏（只想到了 spell，漏了 listen）。
2. **分析时注意力被带偏**：跑完听音选词，我的注意力落在了「干扰项词性混杂」「零基础看不懂音标」「答错后文案名不副实」上，反而漏掉了更基础的「这题泄题了」。
3. **intent 写了却没执行**：persona 里背单词任务的 intent 明明写了「题目是否泄露答案」，但分析时没有逐条核对，被其他发现冲掉了。

### 更深一层：这类 bug 的特点

「答案泄露」这类 bug 的特征是——**不报错、不崩溃、布局还很好看**。脚本抓文本、抓报错、截图，一切显示「正常」。它需要的是**语义联想**：把「显示了单词」和「题目要求听发音选词」两件事联系起来，推出「矛盾」。

这种语义矛盾：
- 脚本做不到（没有语义理解）
- AI 需要「主动代入 + 逐条核对业务规则」才能做到
- **用户一眼就能发现**——因为用户是在「真实地做题」，做题时会本能地利用一切线索，瞬间就意识到「这题不用听，看顶部就能答」

### 对方法论的关键补丁

「用户旅程模拟」不仅要**走**用户的路径，还要**做**用户的任务。光浏览截图是不够的——如果当时真的以小明身份「试图答这道听音题」，就会本能地先看顶部单词，立刻意识到泄题。

**补丁：任务走查时，对每一道题「真实作答」而不是「截图浏览」。** 代入感是发现这类「语义矛盾 bug」的关键，它比任何规则清单都更接近用户的第一反应。

### 三条可执行的改进

1. **修 bug 后强制举一反三**：每修一个 bug，追问「同类 bug 还在哪些地方存在？」（正向列举完整）。
2. **渲染条件用正向列举**：写 `showWord = meaning || pronounce`，而不是 `!isSpell`。前者是「白名单」，后者是「黑名单」，黑名单永远容易漏。
3. **任务走查 = 真实作答**：分析时不只看「页面有什么」，而是「如果我是这个用户，我下一步会怎么利用页面上的信息」。让脚本/分析模拟真实作答，而不是浏览。
